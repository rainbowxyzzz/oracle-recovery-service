# Oracle 双字符集自动路由闭环验证报告（2026-09-17）

## 验证目标

验证系统在收到 Oracle 数据泵备份（DMP）后，能够先在默认 `ZHS16GBK` 字符集的 Oracle 21c 中执行元数据探测；当探测确认源备份为 `AL32UTF8` 且导入默认库存在字符丢失风险时，自动切换到 `AL32UTF8` 字符集的 Oracle 21c，再完成正式还原与结果校验。

## 验证环境

- 验证服务器：`192.168.150.128`
- 默认 Oracle：`oracle-recovery-oracle21c-ee`，服务 `ORCLPDB1`，字符集 `ZHS16GBK`
- UTF Oracle：`oracle-recovery-oracle21c-utf8`，服务 `ORCLPDBUTF8`，字符集 `AL32UTF8`
- 两个数据库的国家字符集均为 `AL16UTF16`
- UTF Oracle 与默认 Oracle 使用独立数据目录，共享只读来源一致的 DMP 宿主目录

## 测试数据

在 UTF Oracle 中创建隔离源模式 `UTF_AUDIT_SRC`，模拟真实审计案件登记业务，包含：

- 1 张案件登记表，3 条含中文姓名、案件摘要、身份证号和联系电话的数据；
- 2 个视图；
- 1 个索引、1 个序列、1 个触发器、1 个存储过程；
- 中文表注释和包含补充字符、表情符号的注释。

使用 Oracle 数据泵导出工具按模式导出，生成 `UTF_AUDIT_SRC_20260916.dmp`。导出成功，业务表共 3 行。

## 系统判断过程

1. 系统读取导出日志。该 Oracle 21c 日志未明确输出源字符集，因此不能仅靠日志直接选库。
2. 系统按默认路由选择 `oracle-recovery-oracle21c-ee / ORCLPDB1 / ZHS16GBK`。
3. 系统使用数据泵的 `SQLFILE`（仅解析元数据、不写入业务对象）执行探测。
4. 数据泵进程返回码为 `0`，但日志明确显示：源备份为 `AL32UTF8`、目标库为 `ZHS16GBK`，并出现“可能发生字符丢失”的警告。
5. 系统没有把返回码 `0` 当作安全，而是将本次探测分类为 `character_set_incompatible`（字符集不兼容）。
6. 系统生成路由原因 `probe_character_set_incompatible`，自动切换到 `oracle-recovery-oracle21c-utf8 / ORCLPDBUTF8 / AL32UTF8`。
7. 系统在 UTF Oracle 中重新探测，字符集兼容检查通过。
8. 系统完成目标模式准备、表空间映射、正式导入和导入后校验。

## 测试中发现并修复的问题

### 1. 导出日志缺少字符集时，远程命令参数错位

旧逻辑会把空字符集作为空参数继续传给命令行，经过远程 Shell 后丢失，导致参数解析失败。现已改为：可选字符集为空时不传该参数，并新增回归测试。

### 2. 默认库探测已判定字符集不兼容，却被“导出日志缺少模式名”提前终止

旧逻辑先校验探测结果中的模式名，导致字符集不兼容的结果无法进入自动改道路由。现已改为：探测已有明确失败分类时先交给路由层处理；切换到 UTF Oracle 并探测成功后，再执行完整的模式名一致性校验。

## 错误与警告处置说明

- 默认 `ZHS16GBK` Oracle 上的字符丢失警告没有被忽略，它是触发自动切换 UTF Oracle 的依据。
- 手工验证初次使用容器数据库根容器连接时出现 `ORA-39087`，原因是 DMP 目录对象创建在可插拔数据库中；改用 `SYSTEM@ORCLPDBUTF8` 后正常。应用正式流程使用可插拔数据库服务，不受此问题影响。
- 最终 UTF Oracle 正式导入无字符集错误、无被忽略的 Oracle 错误、无无效对象。
